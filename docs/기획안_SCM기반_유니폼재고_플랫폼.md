# 기획안 — SCM·데이터 기반 시공팀 유니폼 재고관리 플랫폼

> **한 줄 정의:** 전국 시공팀의 유니폼 재고를, 흩어진 수기 스프레드시트에서 **하나의 중앙 데이터 + 두 사용자용 화면**으로 옮겨 "재고 가시성"과 "요청 처리"를 자동화한 사내 플랫폼.
> **작성 목적:** 이 플랫폼을 왜 만들었고, 어떤 문제를 어떤 사고의 흐름으로 풀었으며, 그 결과 무엇이 얼마나 좋아졌는지를 **수치·논리 근거**로 정리한 포트폴리오용 기획안.

---

## 0. 요약 (Executive Summary)

- **문제:** 유니폼 재고 데이터가 개인 엑셀/브라우저에 흩어져 있어 ①유실 위험, ②수기 계산 오류, ③시공팀↔관리자 반복 문의, ④단가·정산 재작업이 상존.
- **해결:** "기록이 진실, 재고는 계산 결과"라는 원칙 아래 **중앙 DB + 백엔드 서버 + 역할별 2화면(관리자/시공팀)** 구조로 재설계. 요청은 **슬랙 자동 알림**, 단가는 **권한 분리**로 보호.
- **효과(추정):** 반복 업무 **월 약 23.5시간 / 연 약 282시간** 절감(§4 가정 기반), 수기 계산 오류·데이터 유실 리스크를 **구조적으로 제거**, 재고 가시성 확보로 결품·과잉 판단이 데이터 기반으로 전환.
- **의미:** 단순 전산화가 아니라 **SCM의 핵심(단일 진실 공급원·재고 가시성·재발주 신호)** 을 갖춘 데이터 기반이며, 향후 **AI 수요예측**으로 확장 가능한 토대를 확보.

---

## 1. 왜 만들었나 — 배경과 문제 정의

유니폼 재고 관리는 전형적인 **SCM(공급망 관리)** 문제다. "무엇이, 어디에, 얼마나 있고, 언제 다시 채워야 하는가"를 정확히 알아야 결품(현장 인력이 유니폼을 못 받음)과 과잉(재고·비용 낭비)을 막을 수 있다. 그러나 기존 방식은 이 질문에 제대로 답하지 못했다.

### 기존 방식(수기 구글 스프레드시트)의 4가지 구조적 어려움

| # | 어려움 | 왜 생겼나 | SCM 관점의 손실 |
|---|---|---|---|
| P1 | **데이터 유실·분산** | 파일이 개인 PC·브라우저·여러 버전에 흩어짐 | 단일 진실 공급원 부재 → 신뢰 불가 |
| P2 | **수기 계산 오류** | 현재고를 사람이 수식·셀로 직접 관리 | 재고 정확도 저하 → 결품/과잉 오판 |
| P3 | **반복 문의 병목** | 시공팀이 재고를 알려면 관리자에게 매번 문의 | 정보 비대칭 → 리드타임·인건비 낭비 |
| P4 | **정산·단가 재작업** | 단가 변경 시 과거 청구를 수기로 다시 계산 | 반복 수작업 → 오류·시간 손실 |

> **핵심 통찰:** 위 4가지는 서로 다른 문제처럼 보이지만 뿌리는 하나다 — **"데이터가 한 곳에 없고, 숫자를 사람이 관리한다."** 그래서 해결의 방향도 하나로 모였다: **데이터를 중앙화하고, 계산을 시스템에 맡긴다.**

## 2. 문제를 푼 사고의 흐름 — 한 번에 안 만들고, 단계로 검증

처음부터 큰 시스템을 설계하지 않았다. **"쓰면서 진짜 문제를 찾고, 그 문제가 확인되면 그때 구조를 바꾼다"** 는 흐름으로 접근했다. 개발 기록(6월~8월)이 그대로 이 사고의 흐름이다.

```
[1단계] 일단 쓰게 만든다 (MVP · 6월)
   목적: 진짜 필요한 기능/한계를 빠르게 확인
   결정: 서버 없이 브라우저 하나로 시작, 현재고는 '저장' 대신 '계산'
        │
        │  ← 사용하며 확인된 결정적 한계: 데이터가 개인 브라우저에만 (P1)
        ▼
[2단계] 구조를 바꾼다 (대전환 · 7/29)
   목적: 유실·분산(P1)을 뿌리 뽑기
   결정: 회사 중앙 DB + 백엔드 서버.  '화면 → 서버 → DB'
        비밀번호는 서버에만, 계산은 DB 뷰로 (P2 해결)
        │
        │  ← 데이터가 중앙에 모이자 새 기회가 열림: 두 번째 사용자(시공팀)
        ▼
[3단계] 서비스로 넓힌다 (완성 · 7/30)
   목적: 문의 병목(P3)·정산 재작업(P4) 해소
   결정: 시공팀 공개 화면 + 슬랙 자동 요청 + 단가 권한 분리
        │
        ▼
[4단계] 운영을 정리한다 (8월)
   목적: 배포·접근 경로 단순화, 거버넌스 준수
   결정: 사내 서버 일원화 + 잘못된 접속 안내
```

이 흐름의 특징은 **"문제 확인 → 결정 → 그 결정이 낳은 다음 문제 → 다음 결정"** 으로 이어지는 점이다. 각 단계의 결정이 다음 단계의 기회를 열었다(예: 데이터 중앙화가 "시공팀 셀프 조회"를 가능하게 함).

## 3. 해결책 — 무엇을 어떻게 자동화·구조화했나

### 3-1. 구조 (SCM의 "단일 진실 공급원" 구현)

```
[🧑‍💼 관리자 화면] ─┐
                    ├──▶ [🖥️ 서버] ──▶ [🗄️ 회사 중앙 DB]  ← 단 하나의 진실
[👷 시공팀 화면]  ─┘         │
                            └──▶ [💬 슬랙 자동 알림]
```

### 3-2. 문제 → 해결 매핑

| 기존 문제 | 해결한 방식 | 적용된 원리 |
|---|---|---|
| P1 유실·분산 | 중앙 DB + 아웃박스(끊겨도 재전송) | 단일 진실 공급원, 내결함성 |
| P2 계산 오류 | 현재고를 저장하지 않고 **기록 합산으로 자동 계산**(뷰) | "기록이 진실, 재고는 결과" |
| P3 문의 병목 | 시공팀 **셀프 조회 화면** + **재발주 필요 지표** | 재고 가시성, 셀프서비스 |
| P4 정산 재작업 | 단가 변경 시 과거 청구 **자동 소급** + CSV 내보내기 | 자동화, 데이터 기반 정산 |
| (보안) 단가 노출 | 공개 API에서 단가 제외, 비번 통과 시에만 제공 | 최소 권한 원칙 |

### 3-3. SCM 핵심 요소로 본 이 플랫폼

- **재고 가시성(Visibility):** 누구나(권한 내) 실시간 현재고를 같은 값으로 본다.
- **단일 진실 공급원(Single Source of Truth):** 모든 판단이 하나의 DB에서 나온다.
- **재발주 신호(Reorder Signal):** 안전재고 대비 '부족/품절'을 '재발주 필요'로 집계 → 결품 선제 대응.
- **수요 신호 수집(Demand Signal):** 시공팀 요청이 슬랙+데이터로 정형화되어 쌓인다(→ 향후 예측의 입력값).

## 4. 효과 — 수치적 근거 (추정 모델)

> ⚠️ **아래 수치는 실제 측정값이 아니라 합리적 '가정치'에 기반한 추정입니다.**
> 가정 표(4-1)의 값을 실제 값으로 바꾸면 4-2의 결과가 그대로 갱신되는 구조로 정리했습니다.

### 4-1. 가정 표 (← 실제 값으로 교체용)

| 코드 | 가정 항목 | 예시 값 |
|---|---|---|
| A1 | 관리 품목(SKU) 수 | 약 200 |
| A2 | 지역 센터 수 | 12 |
| A3 | 월 유니폼 요청 건수 | 60건 |
| A4 | 요청 1건 처리시간 (취합·재고확인·기록) | 기존 15분 → 개선 4분 |
| A5 | 월 재고 문의(시공팀↔관리자 왕복) | 40건 × 10분(양측 합) → 개선 0분(셀프조회) |
| A6 | 단가 변경 후 과거 청구 수기 재계산 | 월 2회 × 30분 → 개선 0분(자동 소급) |
| A7 | 데이터 유실·재작업 사고 | 분기 1회 × 4시간 복구 → 개선 0(중앙 DB) |
| A8 | 월 정산·현황 취합(엑셀 집계) | 기존 4시간 → 개선 0.5시간(CSV 내보내기) |

### 4-2. 절감 효과 (위 가정 기준 계산)

| 항목 | 계산식 | 월 절감 |
|---|---|---|
| 요청 처리 | 60건 × (15−4)분 | **11.0시간** |
| 재고 문의 제거 | 40건 × 10분 | **6.7시간** |
| 단가 재계산 자동화 | 2회 × 30분 | **1.0시간** |
| 유실 복구 제거 | (분기 4시간) ÷ 3개월 | **1.3시간** |
| 정산 취합 단축 | 4 − 0.5시간 | **3.5시간** |
| **합계** | | **≈ 23.5시간 / 월** |
| **연 환산** | 23.5 × 12 | **≈ 282시간 / 년** |

> **정량 요약(가정 기준):** 반복 업무 **연 약 282시간**(≒ 근무일 35일분) 절감. 여기에 **오류·유실로 인한 비정형 손실**(재작업, 결품 대응, 신뢰 저하)은 별도로, 구조적으로 **0에 수렴**.

### 4-3. 논리적(정성) 근거 — 수치로 다 안 잡히는 이득

- **오류율:** 현재고를 사람이 안 고치므로 **계산 실수 자체가 발생 불가**(기록만 맞으면 항상 정확).
- **유실 리스크:** 개인 기기 의존 제거 + 끊겨도 재전송(아웃박스) → **"언젠가 한 번 크게 터지는" 사고**를 원천 차단.
- **정보 비대칭 해소:** 시공팀이 직접 보고 요청 → 관리자는 '문의 응대'가 아닌 '재고 운영'에 집중.
- **의사결정 전환:** '감'으로 발주하던 것을 **재발주 필요 지표**로 → 결품/과잉을 데이터로 판단.
- **감사 추적성:** 활동 로그로 "누가·언제·무엇을" 추적 → 책임·신뢰 확보.

## 5. SCM·AI 활용 관점 — 지금과 다음

### 5-1. 지금(구현 완료) — "AI를 위한 전제조건"을 만든 단계
현재 플랫폼의 본질은 **데이터 정합성 + 자동화 + 가시성**이다. 이는 AI 도입의 필수 전제다. 아무리 좋은 예측 모델도 **깨끗하고 중앙화된 데이터**가 없으면 무용하기 때문이다. 이 플랫폼은 그 토대(정형화된 수불·요청·재고 데이터)를 확보했다.

### 5-2. 다음(확장 로드맵) — AI로 고도화 가능한 지점

| 단계 | 확장 아이디어 | 입력이 되는 기존 데이터 | 기대 효과 |
|---|---|---|---|
| 1 | **수요예측** (센터·계절·사이즈별 소요량) | 수불·요청 이력 | 선제 발주 → 결품↓ |
| 2 | **안전재고 자동 산정** | 소요 변동성 + 리드타임 | 과잉·결품 동시 최소화 |
| 3 | **이상탐지** (비정상 분출·재고 급변) | 활동 로그·수불 패턴 | 오류·부정 조기 발견 |
| 4 | **요청 자동 분류/추천** | 요청 텍스트·센터 이력 | 요청 처리 자동화 확대 |

> **메시지:** "지금은 규칙 기반 자동화, 다음은 데이터 기반 예측." 이 플랫폼은 그 전환을 **데이터부터** 준비한 설계다.

## 6. 결론

이 플랫폼은 "재고 앱을 하나 만들었다"가 아니라, **팀이 겪던 반복적·구조적 문제를 SCM 관점에서 재정의하고, 데이터 중앙화라는 하나의 원인부터 단계적으로 해결한** 결과물이다.

- **왜:** 흩어진 데이터·수기 계산이 유실·오류·병목·재작업을 낳았다.
- **어떻게:** "기록이 진실, 재고는 계산"이라는 원칙으로 중앙 DB·백엔드·역할별 2화면·자동 알림을 단계적으로 구축했다.
- **결과:** 반복 업무 **연 약 282시간(가정 기준)** 절감 + 오류·유실 리스크 구조적 제거 + 재고 가시성 확보 + **AI 확장 토대** 마련.
