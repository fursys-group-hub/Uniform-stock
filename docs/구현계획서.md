## 0. 현재 구조 진단 (As-Is)

| 항목 | 현재 상태 |
|------|-----------|
| 아키텍처 | 순수 정적 웹앱 (HTML + 바닐라 JS + CSS), 백엔드/프레임워크 없음 |
| 데이터 저장 | **브라우저 `localStorage` 단독** (`STORAGE_KEY = 'inventory_mvp_v1'`) |
| 상태 구조 | `state = { items[], transactions[], audits[] }` |
| 현재고 계산 | `initialStock + Σ(부호 있는 수량)` — 클라이언트에서 실시간 계산 (`getCurrentStock`) |
| 로그인 | **없음** — URL만 알면 누구나 전체 기능(등록·수정·삭제·단가) 접근 가능 |
| 관리자 비번 | `app.js`의 `ADMIN_PASSWORD` 상수. 배포 시 `docker-entrypoint.sh`가 `sed`로 주입 → **브라우저 소스보기로 노출됨.** 현재는 수불 수정/삭제 시에만 확인용으로 사용 |
| 백업 | 수동 JSON 다운로드 / 업로드 (`downloadBackup`, `restoreBackup`) |
| 배포 | `nginx:alpine` 컨테이너, `docker-entrypoint.sh`가 env(`ADMIN_PASSWORD`) 주입 후 nginx 실행 |
| 이미지 | 실사 점검 사진을 base64로 압축해 `state`에 인라인 저장 |

### 데이터 유실(#4)의 근본 원인
`localStorage`는 **브라우저 + 도메인(origin) 단위**로만 저장됩니다. 따라서:
- 다른 PC/브라우저에서 접속하면 데이터가 **아예 없음** (기기 간 공유 불가)
- 브라우저 캐시/사이트 데이터 삭제 시 **소멸**
- 배포 도메인·경로가 바뀌면 이전 origin의 데이터에 **접근 불가**
- **중앙 사본이 없어** 한 사람 브라우저에만 존재 → 사실상 백업이 없는 상태

> 참고: 컨테이너를 재배포해도 도메인이 같으면 사용자 브라우저의 localStorage 자체는 유지됩니다. 그럼에도 "보수하면 날아간다"고 느껴진 이유는 위 4가지(도메인 변경/캐시 삭제/다른 기기·브라우저 사용) 중 하나일 가능성이 큽니다. **해결책은 동일합니다 — 중앙 DB(Supabase)로 이전.**

## 1. 목표 구조 (To-Be)

```
[시공팀 브라우저] ──(읽기 전용, 실시간)──┐
[관리자 브라우저] ──(로그인 후 읽기/쓰기)─┤
                                          ▼
                                  ┌──────────────┐
                                  │   Supabase    │
                                  │  - Postgres   │  ← 수불/재고/실사/로그 영구 저장 (단일 진실원본)
                                  │  - Auth       │  ← 관리자 로그인
                                  │  - Realtime   │  ← 재고 변동 실시간 푸시
                                  │  - Storage    │  ← 실사 이미지
                                  └──────────────┘
```

핵심 전환: **"localStorage 단독" → "Supabase가 단일 진실원본(source of truth), localStorage는 오프라인 캐시/재시도 큐"**

## 2. 핵심 설계 결정 & 보안 주의사항

1. **Supabase anon key는 공개 정보다.** 정적 사이트에서는 키가 JS에 노출될 수밖에 없다. 보안은 키 은닉이 아니라 **RLS(Row Level Security) 정책**으로 만든다.
   - 익명(anon): `items`, `current_stock` **읽기만** 허용 (공개 대시보드용)
   - 인증(authenticated): 전체 읽기/쓰기 허용 (관리자)
   - `transactions`(담당자·청구액 포함), `audits`, `activity_logs`는 **익명 접근 차단** → 공개 대시보드에는 재고 수량만 노출, 개인정보/청구정보는 비노출
2. **관리자 비밀번호를 클라이언트에서 비교하지 않는다.** 현재 방식(`pw === ADMIN_PASSWORD`)은 소스에 비번이 박혀 무력하다. 대신 **Supabase Auth 계정**으로 로그인해 서버가 검증한다. 코드에는 비번이 남지 않는다.
   - 로그인 화면: `관리자명(수동입력)` + `비밀번호`. 비밀번호는 고정 관리자 계정(`Letus2026!@`)으로 Supabase 인증. `관리자명`은 "누가 작업했는지" 기록용 라벨로 각 수불/로그에 함께 저장.
3. **쓰기는 항상 write-through + 아웃박스(재시도 큐).** 모든 등록/수정/삭제는 ① 로컬 상태 즉시 반영(화면) → ② Supabase 반영. 네트워크 실패 시 localStorage 아웃박스에 쌓고 재시도 → **작업 중 유실 0 보장.**
4. **공개(Phase 3)는 반드시 로그인+RLS(Phase 2) 완료 후.** URL이 외부에 퍼지는 시점 전에 쓰기 권한이 잠겨 있어야 한다. (안전 불변식)
5. **supabase-js는 저장소에 동봉(vendoring)** 권장 — CDN 장애/사내망 제약에 영향받지 않도록 UMD 빌드를 repo에 포함.
6. **줄바꿈**: 저장소는 CRLF로 커밋되어 있음. 파일 편집 시 줄바꿈 정규화 이슈 주의(필요 시 `.gitattributes` 별도 도입).

## 3. Supabase 스키마 (초안 DDL)

```sql
-- 품목 마스터
create table if not exists items (
  id            text primary key,
  category      text not null,
  name          text not null,
  size          text not null,
  unit_price    numeric not null default 0,
  initial_stock integer not null default 0,
  safety_stock  integer not null default 0,
  updated_at    timestamptz not null default now()
);

-- 수불(입고/분출/반납/조정/실사조정/잉여출고)
create table if not exists transactions (
  id         uuid primary key default gen_random_uuid(),
  date       date not null,
  type       text not null check (type in ('입고','분출','반납','재고조정','실사조정','잉여출고')),
  item_id    text not null references items(id),
  quantity   integer not null,
  issuer     text default '',
  receiver   text default '',
  note       text default '',
  unit_price numeric not null default 0,
  amount     numeric not null default 0,
  created_by text default '',              -- 작업한 관리자명
  created_at timestamptz not null default now()
);

-- 실사
create table if not exists audits (
  id          uuid primary key default gen_random_uuid(),
  date        date not null,
  inspector   text not null,
  item_id     text not null references items(id),
  system_qty  integer not null,
  counted_qty integer not null,
  diff_qty    integer not null,
  note        text default '',
  image_path  text default '',             -- Supabase Storage 경로 (초기엔 base64 컬럼도 허용)
  created_by  text default '',
  created_at  timestamptz not null default now()
);

-- 조작/접속 로그
create table if not exists activity_logs (
  id     bigint generated always as identity primary key,
  at     timestamptz not null default now(),
  actor  text default '',                  -- 관리자명
  action text not null,                    -- login / tx_create / tx_update / tx_delete / price_update / audit_create ...
  target text default '',
  detail jsonb
);

-- 현재고 뷰 (대시보드/실시간용)
create or replace view current_stock as
select
  i.id as item_id, i.category, i.name, i.size, i.unit_price, i.safety_stock,
  i.initial_stock + coalesce(sum(
    case t.type
      when '입고'   then t.quantity
      when '반납'   then t.quantity
      when '분출'   then -t.quantity
      when '잉여출고' then 0
      else t.quantity            -- 재고조정, 실사조정
    end), 0) as current_stock
from items i
left join transactions t on t.item_id = i.id
group by i.id;
```

### RLS 정책 요약
```sql
alter table items enable row level security;
alter table transactions enable row level security;
alter table audits enable row level security;
alter table activity_logs enable row level security;

-- 익명: 재고 마스터 읽기만 (대시보드)
create policy "anon read items" on items for select to anon using (true);
-- current_stock 뷰는 items/transactions 기반 → 뷰 전용 노출은 security definer 함수 또는 별도 grant로 처리

-- 인증(관리자): 전체 권한
create policy "auth all items"        on items        for all to authenticated using (true) with check (true);
create policy "auth all transactions" on transactions for all to authenticated using (true) with check (true);
create policy "auth all audits"       on audits       for all to authenticated using (true) with check (true);
create policy "auth insert logs"      on activity_logs for insert to authenticated with check (true);
```
> 공개 대시보드가 `current_stock`만 보게 하는 방법은 Phase 3 착수 시 확정(뷰 grant vs `security definer` RPC 함수). 이렇게 하면 익명은 **재고 수량만** 보고 담당자·청구액은 못 본다.

## 5. 단계별 구현 계획

각 Phase는 **독립 배포 가능**하며, 완료기준(테스트)을 통과해야 다음으로 넘어간다.

### ✅ Phase 1 — Supabase 영구 저장 도입 (해결: #4, #3의 데이터 부분) — **최우선**
**목표:** 데이터를 중앙 DB에 영구 저장해 유실 위험을 제거한다. 화면/UX는 그대로 유지.

**작업**
1. Supabase 프로젝트 생성, 위 DDL로 테이블/뷰 생성
2. supabase-js 동봉 + `config.js` 로딩 + 클라이언트 초기화
3. 데이터 계층 추상화: 현재 `state` 직접 접근 → `dataStore` 모듈(읽기/쓰기 함수)로 감싸기
4. **초기 이관(마이그레이션)**: 앱 로드시 Supabase가 비어있고 localStorage에 데이터가 있으면 → 자동으로 Supabase에 일괄 업로드 (기존 데이터 보존). `seedItems`는 `items`에 upsert.
5. **write-through + 아웃박스**: 등록/수정/삭제 시 로컬 즉시 반영 후 Supabase 반영, 실패 시 재시도 큐 적재
6. 읽기 경로: 로드시 Supabase에서 fetch → 없으면 localStorage 폴백

**변경 파일:** `app.js`(데이터 계층), `index.html`(스크립트 로딩), `Dockerfile`/`docker-entrypoint.sh`/`.env.example`, `vendor/supabase.js`(신규)

**완료기준(테스트)**
- [ ] 수불 등록 후 Supabase 테이블에 행이 생김
- [ ] 브라우저 캐시를 지워도(=localStorage 삭제) 데이터가 그대로 보임
- [ ] 다른 브라우저/기기에서 접속해도 동일 데이터가 보임
- [ ] 오프라인 상태에서 등록 → 온라인 복귀 시 자동 동기화

**롤백:** 데이터 계층에 `USE_SUPABASE` 플래그. 문제 시 false로 되돌리면 기존 localStorage 동작. (데이터는 이미 Supabase에도 있으므로 안전)

**커밋 예:** `feat: Supabase 영구 저장 도입 및 기존 데이터 자동 이관`

### ✅ Phase 2 — 로그인 & 권한 분리 (해결: #1, #2)
**목표:** 로그인 없이는 조회만/차단, 관리자만 등록·수정·삭제.

**작업**
1. Supabase Auth에 고정 관리자 계정 생성(비번 `Letus2026!@`)
2. 로그인 화면 추가: `관리자명(수동입력)` + `비밀번호`. 인증 성공 시 관리자 모드 진입, `관리자명`을 세션에 저장해 이후 수불/로그의 `created_by`로 사용
3. RLS를 "인증=쓰기, 익명=제한" 으로 확정 → 실제 보안 경계가 DB에 생김
4. 기존 `ADMIN_PASSWORD`/`verifyAdmin` 정리: 로그인으로 대체(수정·삭제 시 중복 프롬프트 제거 여부 결정)
5. 로그아웃 버튼, 세션 유지(supabase 세션) 처리

**변경 파일:** `index.html`(로그인 뷰), `app.js`(auth 로직/가드), `styles.css`(로그인 UI), 배포 스크립트(비번 주입 제거)

**완료기준**
- [ ] 로그아웃 상태에서 등록/수정/삭제 시도 불가(UI 숨김 + DB에서도 거부)
- [ ] 올바른 비번으로만 로그인, 틀리면 거부
- [ ] 로그인한 관리자명이 신규 수불의 작업자로 기록됨
- [ ] 새로고침해도 로그인 유지

**커밋 예:** `feat: 관리자 로그인 도입 및 RLS 기반 권한 분리`

### ✅ Phase 3 — 공개 실시간 재고 대시보드 (해결: #5)
**목표:** 로그인 없이 누구나 볼 수 있는 **읽기 전용** 재고현황 페이지. 시공팀이 직접 실시간 확인.

**작업**
1. 공개 뷰 분리: `dashboard.html`(별도 경량 페이지) 또는 `?view=public` 라우팅. 관리 UI(등록/수정/단가/청구) **완전 제외**
2. `current_stock` 뷰만 조회 (담당자·청구액 비노출)
3. **Supabase Realtime 구독**: `transactions`/`items` 변경 시 자동 재조회·재렌더 → 관리자가 분출 등록하면 시공팀 화면이 즉시 갱신
4. 검색/분류 필터, 모바일 반응형(현장에서 폰으로 확인)
5. (선택) 공개 URL은 별도 안내 — 관리 URL과 구분

**완료기준**
- [ ] 로그인 없이 재고 수량 조회 가능, 관리 기능은 노출/접근 불가
- [ ] 관리자가 수불 등록 → 공개 대시보드가 새로고침 없이 갱신
- [ ] 담당자·청구액 등 민감정보 비노출(네트워크 응답에도 없음)
- [ ] 모바일에서 정상 표시

**커밋 예:** `feat: 공개 실시간 재고 대시보드 추가`
