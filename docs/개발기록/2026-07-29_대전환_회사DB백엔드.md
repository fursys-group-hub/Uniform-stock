## 🔍 깊게 보기 ① 왜 "화면 → 서버 → DB" 구조로 바꿨을까? (비전공자용 쉬운 설명)

이 날의 가장 큰 변화예요. 예전엔 브라우저가 데이터를 직접 다뤘는데, 이제는 **중간에 '서버'** 가 생겼어요.

### 1. 한 줄 요약
화면(브라우저)이 회사 DB에 **직접 붙지 않고**, 가운데 둔 **서버에게 부탁**하는 구조로 바꿨어요. DB 비밀번호는 **서버만** 알고 화면은 몰라요.

### 2. 왜 이렇게 했을까? (핵심 오해 풀기)
회사가 전용 DB를 줬을 때, "브라우저가 바로 DB에 붙으면 되지"라고 생각하기 쉬워요. 그런데 그러면 큰일 나요.

❌ **브라우저가 DB에 직접 접속** — 접속하려면 DB 비밀번호가 필요한데, 그 비번이 **화면 코드에 들어가** 누구나 개발자 도구로 열어볼 수 있음. 사내 DB가 통째로 위험.

✅ **가운데 서버를 둠** — 화면은 서버에게만 "재고 주세요" 부탁하고, 서버가 DB에 대신 다녀옴. DB 비밀번호는 **서버 안에만** 있어 화면엔 없음.

> **비유:** 손님이 주방(DB) 금고에 직접 들어가는 게 아니라, 직원(서버)에게 주문하면 직원만 금고를 여는 것과 같아요. 금고 열쇠(비번)는 손님 손에 절대 안 가요.

### 3. 전체 흐름 (그림)

```
❌ Before (6~7월)
   [브라우저] ───직접──▶ [데이터]     (비번이 화면에 노출될 판)

✅ After (7/29~)
   [브라우저] ──부탁──▶ [서버] ──질의──▶ [회사 DB]
                         │
                    DB 비번·열쇠는
                    여기에만 보관
```

### 4. 코드에서는 어디서 (파일별 역할)
| 단계 | 파일 | 하는 일 |
|---|---|---|
| DB 접속(비번 보관) | `server/server.js` | 접속정보를 **환경변수**에서만 읽음 (코드/화면엔 없음) |
| 화면의 부탁 받기 | `server/server.js` | `/api/...` 요청을 받아 DB에 대신 질의 |
| 부탁 보내기 | `public/app.js` | 서버에 요청만 보냄 (DB를 모름) |

```js
// server/server.js — 접속정보는 서버 환경변수에서만
const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,   // 화면엔 절대 안 감
  options: `-c search_path=${DB_SCHEMA},public`  // 회사 전용 공간으로 고정
});
```

### 5. 자주 나올 질문 (Q&A)
**Q. 서버가 하나 더 생기면 복잡하지 않나요?** → 관리 포인트는 늘지만, 그 대가로 **비밀 보호 + 권한 통제 + 여러 사람 공유**를 얻어요. 중앙 데이터엔 필수예요.
**Q. 브라우저가 DB에 직접 붙는 앱도 있잖아요?** → 있어요. 하지만 그건 접근 규칙을 아주 촘촘히 건 경우고, 사내 DB를 그렇게 여는 건 부담이 커서 서버 경유를 택했어요.

### 6. 핵심만 다시
- 화면은 DB에 **직접 안 붙고 서버에 부탁** → DB 비번이 화면에 없음(안전)
- 로그인·권한·검증을 **서버 한 곳**에서 통제 → 확장·보안의 토대

## 🔍 깊게 보기 ② 인터넷이 끊겨도 입력이 왜 안 사라질까? (재시도 큐 = 아웃박스)

현장에서 인터넷이 잠깐 끊겨도, 입력한 수불이 사라지지 않아요. 어떻게요?

### 1. 한 줄 요약
저장할 때 **화면에 먼저 반영**하고 **대기열에 적어둔 뒤** 서버로 보내요. 전송이 실패하면 대기열에 **남아 있다가 연결되면 자동으로 다시** 보내요.

### 2. 왜 이렇게 했을까? (핵심 오해 풀기)
❌ **바로 서버로만 보내는 방식** — 보내는 순간 인터넷이 끊기면 그 입력은 **그냥 사라짐.**

✅ **대기열(아웃박스) 방식** — 일단 대기열에 적어두니, 전송이 실패해도 기록은 남음. 연결되면 **순서대로 재전송.**

> **비유:** 편지를 손에 들고 우체통까지 뛰어가다 놓치면 잃어버리지만(❌), 일단 '보낼 편지함'에 넣어두면 집배원이 올 때까지 안전한 것(✅)과 같아요.

### 3. 전체 흐름 (그림)

```
① 수불 입력
     ▼
② 화면에 먼저 반영 + '보낼 함(대기열)'에 적어둠
     ▼
③ 서버로 전송 시도
     ├─ 성공 → 대기열에서 지움 ✅
     └─ 실패(끊김) → 대기열에 그대로 둠
                       │
                 연결되면 ④ 자동 재전송 (맨 앞부터 순서대로)
```

### 4. 코드에서는 어디서 (파일별 역할)
| 단계 | 파일 | 하는 일 |
|---|---|---|
| ② 대기열 적재 | `public/app.js` | `enqueue` — 작업을 대기열에 넣음 |
| ③④ 순서대로 재전송 | `public/app.js` | `flushOutbox` — 성공한 것만 지우고 실패하면 멈췄다 재시도 |

### 5. 자주 나올 질문 (Q&A)
**Q. 순서가 뒤섞이지 않나요?** → 항상 맨 앞부터 처리하고 성공한 것만 지워서 순서가 지켜져요.
**Q. 브라우저를 닫으면요?** → 대기열은 브라우저에 저장돼 있어, 다시 열면 이어서 보내요.

### 6. 핵심만 다시
- 저장 = **화면 먼저 → 대기열 → 서버** 순서
- 끊겨도 **대기열에 남아 자동 재전송** → 입력 유실 없음

## 🔍 깊게 보기 ③ 로그인은 어떻게 "관리자만" 걸러낼까? (토큰 방식)

### 1. 한 줄 요약
비밀번호가 맞으면 서버가 **출입증(토큰)** 을 하나 발급해요. 이후 요청엔 이 출입증을 붙여 보내고, 서버는 출입증이 유효할 때만 처리해요.

### 2. 왜 이렇게 했을까?
중앙 데이터가 되면 아무나 수정하면 안 돼요. 그렇다고 요청마다 비밀번호를 계속 보내는 건 위험하고 번거로워요. 그래서 **한 번 로그인 → 출입증 발급 → 이후엔 출입증으로** 방식을 썼어요.

> **비유:** 건물에 들어갈 때 한 번 신분 확인 후 **방문증**을 받고, 이후엔 방문증만 보여주면 되는 것과 같아요. (방문증엔 유효시간이 있어요 — 12시간)

### 3. 전체 흐름 (그림)

```
① 관리자: 비밀번호 입력
      ▼
② 서버: 맞으면 출입증(토큰) 발급  (12시간 유효)
      ▼
③ 이후 모든 요청에 출입증을 붙여 보냄
      ▼
④ 서버: 출입증 확인 → 유효하면 처리, 아니면 거절(재로그인)
```

### 4. 핵심만 다시
- 로그인 1회 → **토큰 발급** → 이후엔 토큰으로 인증
- 토큰 없으면/만료면 거절 → **관리자만** 데이터 수정

## 🤔 고민 과정 (기록용)

- **가장 큰 불안은 "언젠가 데이터가 통째로 날아간다"였다.** MVP는 브라우저에만 데이터가 있어 기기 교체·캐시 삭제 한 번에 끝이었다. 회사가 전용 DB를 배정해준 게 전환의 결정적 계기.
- **"브라우저가 DB에 직접 붙이면 되지 않나?"를 진지하게 검토했고, 접었다.** DB 접속엔 비밀번호가 필요한데 그게 화면 코드에 실린다. 사내 DB를 그렇게 열 순 없어서 **중간 서버**를 두기로 했다 — 이게 이 날 구조의 핵심 결정이다.
- **전환 중 데이터 유실이 제일 무서웠다.** 그래서 옮기면서 기존 로컬 데이터를 **자동 이관**했고, 현장 네트워크가 불안정할 걸 대비해 **아웃박스**를 넣었다. "새 구조로 옮기다 오히려 잃는" 최악을 피하려는 안전장치들이다.
- **중앙 데이터가 되니 자연히 따라온 것들** — 아무나 못 고치게 하는 **로그인**, 누가 언제 뭘 바꿨나 남기는 **활동 로그**, 시공팀이 직접 보게 할 **조회 대시보드**의 토대. 하나를 바꾸니 필요한 게 줄줄이 드러난 날이었다.

### ② 데이터 그릇 + 현재고 뷰 (`supabase/schema.sql`)
현재고를 저장하지 않고 **뷰로 계산** — MVP의 계산 규칙을 SQL로 옮긴 것.
```sql
create view current_stock as
select i.id as item_id, ...,
  i.initial_stock + coalesce(sum(
    case t.type
      when '입고' then t.quantity   when '반납' then t.quantity
      when '분출' then -t.quantity  when '잉여출고' then 0
      else t.quantity              -- 재고조정·실사조정
    end), 0) as current_stock
from items i left join transactions t on t.item_id = i.id
group by i.id;
```

```js
}
```

### ④ 아웃박스 — 끊겨도 안 잃는 재시도 큐 (`public/app.js`)
저장 작업을 큐에 넣고, 성공한 것만 지우며 순서대로 전송한다.
```js
function enqueue(op) { const q = loadOutbox(); q.push(op); saveOutbox(q); flushOutbox(); }

async function flushOutbox() {
  while (true) {
    const q = loadOutbox(); if (!q.length) break;
    try { await applyOp(q[0]); }            // 맨 앞부터 실제 전송
    catch { break; }                        // 실패 → 순서 보존 위해 멈춤(다음 기회 재시도)
    const q2 = loadOutbox(); q2.shift(); saveOutbox(q2);   // 성공분만 제거
  }
}
// applyOp: op.type에 따라 알맞은 API 호출 (insertTx / updateTx / insertAudit / log ...)
```
