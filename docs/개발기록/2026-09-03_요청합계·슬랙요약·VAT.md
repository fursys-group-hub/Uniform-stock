## 🔍 깊게 보기 — 요청 합계는 어떻게 나오나 (비전공자용)

### 1. 한 줄 요약
매주 여러 권역이 보낸 요청을, **같은 품목·사이즈끼리 더해서** "창고에 준비할 총 수량"을 냅니다.

### 2. 왜 필요한가
주문은 권역/요청자별로 따로 와야 장부 입력이 안 헷갈려요(그건 유지). 하지만 **창고 준비** 는 결국 "동일 품목·사이즈를 합쳐서" 하니까, 그 합산을 자동으로.

### 3. 흐름 (그림)
```
[시공팀 /request 요청] ─▶ 슬랙 알림(그대로)  +  DB 저장(uniform_requests) ← 신규
                                                     │
[요청 합계 탭] 기간 선택 ──▶ 그 기간 요청을 품목·사이즈별 합산
                                                     │
                         ▶ [준비 필요 수량]  📨 슬랙 게시 / 📋 복사 / ⬇ 엑셀
```

### 4. 핵심만
- **주문 = 권역별 개별**(장부용) / **준비 = 합산**(창고용) — 둘 다 챙김
- ⚠️ 합산은 **이 기능 배포 이후 요청부터** (과거는 슬랙에만 있었고 저장 안 됨)

## 🤔 고민 과정

- **봇 vs 워크플로 vs 앱** — "슬랙 안에서 `/합산계산`" 은 슬랙 봇이 필요하고(서버를 슬랙이 호출), 봇은 설치·외부접근 등 부담이 컸다. → **관리자 앱에서 계산 후 슬랙 게시** 로 결정(봇 불필요).
- **배포 환경변수 갱신 불가** — 이 사내 배포 시스템은 **기존 앱에 새 env를 못 넣는다**(재배포해도 unchanged). 그래서 요약 웹훅을 env 대신 **DB(`app_config`)에 저장** 하고 서버가 거기서 읽게 우회했다. (이게 이 날의 핵심 설계 결정)
- **요청 저장 형식** — 슬랙엔 문자열로 보냈지만, 합산하려면 **구조화된 lines(품명·사이즈·수량)** 가 필요 → 요청 시 구조화 데이터도 함께 전송·저장.

## 💻 코드는 이렇게 구성했다

| 파일 | 추가/수정 |
|---|---|
| `public/request.html` | 요청 전송 시 구조화 `lines` 함께 전송 |
| `server/server.js` | `uniform_requests`·`app_config` 테이블, `/api/requests`(기간조회)·`/api/requests/notify`(요약 게시), 요약 웹훅 DB fallback |
| `public/app.js` | 요청 합계 탭(`loadRequests`·`aggregateRequests`·`buildReqsumText`·슬랙/복사/엑셀) |
| `server/set-config.mjs` | app_config 값 세팅 유틸 |

```js
// 요청 저장(best-effort — 실패해도 주문은 성공 처리)
insert into uniform_requests (req_date, requester, region, center, lines) ...
// 요약 웹훅: env 없으면 DB에서
const webhook = SLACK_SUMMARY_WEBHOOK || await getConfig('summary_webhook');
```

## 🛠️ 삽질 & 배운 점
- **슬랙 앱 설치 제한** — 회사 슬랙이 앱/통합 설치를 막아 둬서, 요약 게시는 **워크플로(웹훅 트리거)** 로 우회. 서버는 그 웹훅으로 `{text}` 만 보내면 됨.
- **배포 env 한계** → **DB 설정 저장** 이라는 우회가 이 프로젝트의 유용한 패턴이 됐다(웹훅 외 다른 설정도 같은 방식 가능).
