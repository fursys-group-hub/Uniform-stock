## 🔍 깊게 보기 왜 "외부 공개"를 접었을까? (비전공자용 쉬운 설명)

7/30에 "회사 밖에서도 접속하게 할까?" 대비해 외부 호스팅 설정을 준비했었는데, 이 날 그걸 **접었어요.** 이유를 풀어볼게요.

### 1. 한 줄 요약
데이터가 **회사 전용 DB**라, 회사 밖에서 도는 공개 서비스에 그 DB를 연결하는 게 부담이 커서, **사내 서버 한 곳**으로만 운영하기로 했어요.

### 2. 무엇을 저울질했나 (핵심)
두 가지가 서로 부딪혔어요.

- 🟢 **접근성** — 외부에 두면 회사 계정 없는 권역장도 편하게 접속.
- 🔴 **데이터 통제** — 사내 DB를 회사 밖 서비스에 물리는 건 보안·거버넌스상 위험.

→ 이 둘 중 **데이터 통제를 우선**했어요. 편의보다 "사내 데이터는 사내 통제 안에" 원칙이 더 중요했어요.

> **비유:** 손님 편하라고 회사 금고를 건물 밖 공용 창고로 옮기는 셈이라, 편하지만 위험해서 안 하기로 한 거예요.

### 3. 전체 흐름 (그림)

```
검토:  [사내 DB] ──연결?──▶ [회사 밖 공개 서버]   ← 거버넌스상 부담 ❌
결정:  [사내 DB] ──연결───▶ [사내 서버(SSO)]      ← 통제 범위 안 ✅
       (render.yaml 제거)
```

### 4. 핵심만 다시
- 외부 공개 설정(`render.yaml`) **제거**
- 배포처 = **사내 서버 한 곳**으로 단순화 (데이터는 회사 통제 안)
- 회사 계정 없는 외부 접근 문제는 → [8/7 안내 페이지](2026-08-07_github안내페이지.md)에서 별도 정리

## 🤔 고민 과정 (기록용)
- 외부 권역장 접근성을 위해 외부 호스팅을 진지하게 준비했지만, 결국 **"사내 데이터를 회사 밖에 두는 부담"** 을 넘지 못했다.
- 접근성은 포기가 아니라 **다른 방법으로 푼다**로 방향을 틀었다 — 사내 서버(SSO 게이트) 유지 + 잘못 들어온 사람 안내는 [8/7](2026-08-07_github안내페이지.md)에서 처리. "안 되는 걸 억지로"보다 "되는 선에서 최선"을 택한 결정.
