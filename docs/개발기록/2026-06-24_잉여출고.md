## 🔍 깊게 보기 잉여출고는 왜 재고를 안 깎을까? (비전공자용 쉬운 설명)

수불 등록에 '잉여출고'라는 구분이 있어요. 다른 출고(분출)와 달리 이건 **재고 숫자를 줄이지 않아요.** 왜 그럴까요?

### 1. 한 줄 요약
잉여출고는 "나갔다는 사실은 남기되, **재고 수량 계산에는 0으로** 넣는" 구분이에요. 그래서 이력엔 남지만 현재고는 그대로예요.

### 2. 왜 이런 게 필요할까? (핵심 오해 풀기)
현장엔 "정식으로 재고를 깎기는 애매한데, 나간 사실은 남겨야 하는" 출고가 있어요. 이걸 처리할 방법이 두 가지인데 둘 다 문제였어요.

❌ **그냥 분출로 처리** — 재고가 실제보다 적게 깎여서 **숫자가 왜곡**됨.
❌ **아예 기록 안 함** — 나중에 "그거 어디 갔지?" **추적이 끊김**.

✅ **잉여출고 구분** — 기록은 남기고(추적 O), 재고 계산엔 0으로(왜곡 X). 두 문제를 동시에 해결.

> **비유:** 가계부에 "지출로 잡긴 뭣하지만 기록은 해둘 지출"을 메모란에만 적고 잔액 계산에선 빼는 것과 같아요.

### 3. 전체 흐름 (그림)

```
현재고 계산에서 구분별 부호:
   입고    → +수량
   반납    → +수량
   분출    → −수량
   잉여출고 →  0     ◀ 기록만, 재고엔 영향 없음
   재고조정 → ±수량
```

### 4. 코드에서는 어디서 (파일별 역할)
| 단계 | 파일 | 하는 일 |
|---|---|---|
| 부호 0 처리 | `public/app.js` → 이후 `supabase/schema.sql` | 잉여출고만 수량 증감 0으로 |

```sql
-- 현재고 뷰 (7/29 DB 전환 때 반영)
when '잉여출고' then 0   -- 재고 영향 없음, 기록만 남김
```

### 5. 자주 나올 질문 (Q&A)
**Q. 그럼 잉여출고는 어디서 보나요?** → 수불 이력엔 그대로 남아요. 재고 숫자에만 반영이 안 될 뿐이에요.

### 6. 핵심만 다시
- 잉여출고 = **기록 O, 재고 계산 0**
- "재고 정확성"과 "기록 완전성"을 **동시에** 챙기는 장치

## 🤔 고민 과정 (기록용)
- 기존 4개 구분(입고/분출/반납/재고조정)으로는 안 담기는 케이스가 실제로 나왔다. 새 구분을 파는 게 맞나 고민했지만, "분출로 우겨넣기"도 "기록 생략"도 결국 데이터를 망친다고 판단해 **전용 구분**을 만들었다.
- 이 결정 덕에 "현재고 계산은 구분별 부호로 정한다"는 규칙이 명확해졌고, 이후 [7/29 DB 전환](2026-07-29_대전환_회사DB백엔드.md) 때 현재고 뷰에 그대로 옮겨졌다.
