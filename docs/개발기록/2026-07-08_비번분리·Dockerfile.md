## 🔍 깊게 보기 비밀번호를 왜 코드에서 뺐을까? (비전공자용 쉬운 설명)

### 1. 한 줄 요약
비밀번호를 프로그램 코드 안에 적어두지 않고, **프로그램 밖(배포 설정)에 따로 두고** 실행할 때 넣어주는 방식으로 바꿨어요.

### 2. 왜 이렇게 했을까? (핵심 오해 풀기)
❌ **코드에 박아두는 방식** — 소스 코드를 볼 수 있는 사람이면 **누구나 비밀번호를 읽음.** 저장소를 공유하는 순간 노출.

✅ **밖에서 주입하는 방식** — 코드에는 "여기에 비밀번호가 들어온다"는 자리만 있고, 실제 값은 **서버 설정에만** 있음. 코드를 봐도 값은 모름.

> **비유:** 현관 비밀번호를 문에 적어두는 것(❌)과, 문엔 잠금장치만 두고 번호는 관리인만 아는 것(✅)의 차이예요.

### 3. 전체 흐름 (그림)

```
❌ 예전:  코드 안에  password = "Letus..."   ← 소스 보면 노출
✅ 지금:  코드 안에  password = (서버 설정에서 가져옴)
                                    │
                          배포할 때 서버에만 값 주입
```

### 4. 자주 나올 질문 (Q&A)
**Q. 그럼 완전히 안전한가요?** → 이건 '노출 위험을 줄이는' 첫 단계예요. 진짜 검증(맞는 비번인지 서버가 확인)은 [7/29](2026-07-29_대전환_회사DB백엔드.md)에서 완성돼요.

### 5. 핵심만 다시
- 비밀번호는 **코드가 아니라 배포 설정에** → 소스만 봐선 알 수 없음
- 보안의 첫 단추 (완성은 7/29 서버 검증)

## 🤔 고민 과정 (기록용)
- MVP가 자리를 잡으니 "**여러 사람이 사내 서버에서 쓰게 하자**"는 방향이 생겼다. 그러자 코드에 박힌 비밀번호가 걸렸고, 먼저 분리부터 했다.
- 동시에 "배포가 매번 손으로 다르면 안 된다"는 생각에 **Docker**를 처음 도입했다. 이때는 정적 파일을 nginx로 띄우는 형태였고, [7/29 백엔드 전환](2026-07-29_대전환_회사DB백엔드.md) 때 Node 실행형으로 바뀐다. "어느 서버든 같은 방식으로 올린다"는 재현 가능한 배포의 첫 발이었다.

## 💻 코드는 이렇게 구성했다 (기술 상세)

### 손댄 파일
| 파일 | 역할 |
|---|---|
| `public/app.js` | 코드에 박혀 있던 비밀번호 상수 제거(밖에서 주입) |
| `Dockerfile` | 신규 — 사내 서버 배포용(당시 nginx 정적 서빙) |

### 비번 분리 — "값"이 아니라 "자리"만 코드에
코드에는 실제 비밀번호를 두지 않고, 값은 배포 환경이 채우도록 바꿨다. 이 방향은 [7/29](2026-07-29_대전환_회사DB백엔드.md)에서 **서버 환경변수 + 서버 검증**으로 완성된다.
```js
// server/server.js (7/29 이후 최종 형태) — 값은 서버 환경변수에서만
const ADMIN_PASSWORD = process.env.ADMIN_PASSWORD || '';   // 코드엔 값이 없음
```

### Dockerfile 최초 도입
- 당시: 정적 파일을 nginx로 서빙하는 구성.
- 이후 7/29: `node:20-alpine` 기반으로 **Node 실행형**으로 교체(서버가 생겼으므로).
